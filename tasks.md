## Notes for picking this up in a new session

- Spec clarifications beyond v1.0 are in `taskdeck-spec.md` §14 (scope AND/OR semantics, deadline_rule as override, company-creation dimension validation).
- `taskdeck-addendum-v1.1.md` (§15, not yet appended into the main spec file) covers app_settings, configurable calendar edit permissions, absence-aware assignment with instance-level overrides, and member-initiated reassignment requests — tasks 20a–20g. It also has knock-on changes to §6 (timezone becomes `app_settings.timezone` instead of the hardcoded `APP_TIMEZONE` constant in `lib/config.ts`), §7.3, §7.6, §9, and §11 — read it before starting 20a.
- Frontend design reference: `stitch_office_task_pulse/` (mockups + `executive_precision/DESIGN.md` style guide). The app shell built in task 4 predates this and gets realigned to it in task 23.
- Local dev: Supabase runs on non-default ports (see `supabase/config.toml` — shifted +1000 to avoid colliding with other projects on this machine). Colima needs 4 CPU/6GB to run multiple local Supabase stacks at once.
- Every migration must `grant ... to authenticated, service_role` explicitly — this Supabase version doesn't auto-expose new tables to service_role either.
- Never wrap a server action in `startTransition` and pass it via a form's `action=` prop — use `onSubmit` + `preventDefault()` + `new FormData(e.currentTarget)` instead. See the task 11 commit for why.
- The app shell's content column (`AppShell`'s `<div className="flex flex-1 flex-col">`) needed `min-w-0` added — without it, any page with intrinsically-wide content (e.g. the calendar's month view, ~30 columns) pushes the whole page wider instead of scrolling inside its own `overflow-x-auto` container. Keep that in mind for any other wide-content page (e.g. a future data table).
- Task 22: the seed logic moved from `scripts/seed-data.ts`/`scripts/seed.ts` into `src/lib/demo/` (`seed-data.ts`, `seed-demo-data.ts` exporting `seedDemoData()`) so it's callable from both the CLI script and `src/app/api/reset-demo/route.ts` (nightly cron via `CRON_SECRET`, mirroring `/api/generate-instances`, plus an admin POST path). `seed-demo-data.ts` deliberately has no `import "server-only"` — that package's default export throws under plain Node, which would break `pnpm seed`. Everything demo-only is gated on a new `DEMO_MODE` env var (`src/lib/demo/is-demo-mode.ts`) — off by default, since `reset_demo_data()` wipes the whole dataset and this flag is the only thing protecting a real deployment from it.
- Spec §9 says the manual reset button lives "on the demo landing page, admin-only" — but the landing page (`/login`) is pre-auth only (the middleware redirects signed-in users away from it), so an admin-only control can't actually live there. Put it on the Settings page instead (already admin-gated, and `resetDemoDataAction` re-checks both `DEMO_MODE` and role server-side anyway), shown only when `DEMO_MODE` is on.
- Task 23: the demo seed's "Brand" dimension originally used "Comfort"/"Clarion" as example values — those are real Strawberry Hotels brand names and this is a public repo, so they're now the fictional "Nordvik"/"Havstad" everywhere (seed data, `taskdeck-spec.md` examples, test fixtures). Watch for this if adding more brand-flavored demo/test data later.
- Task 23 retheme: `globals.css`'s `:root`/`.dark` now carry the `stitch_office_task_pulse/executive_precision/DESIGN.md` palette (indigo primary, slate neutrals) under the *same* shadcn variable names the app already used, so `Button`/`Badge`/`Card`/`Table`/`Tabs`/`Input` all repainted for free — no component-level color changes needed for that part. `--radius` dropped from `0.625rem` to `0.375rem` to approximate the design's "soft/0.25rem" shape language without breaking existing proportions (cards land almost exactly on the design's 8px target; badges stay full pills regardless since `--radius-4xl` always clears their height). Font switched from Geist to Inter (design mandates Inter) — also fixed a latent bug where `--font-sans` in the `@theme inline` block pointed at itself (nothing defined `--font-sans`, only `--font-geist-sans`), so Geist was likely never actually applied via Tailwind's `font-sans` utility; the Inter font is now named `--font-sans` directly in `layout.tsx` to close that gap.
- `ui/card.tsx`'s default border was a near-invisible `ring-foreground/10` — bumped to a real `border border-border` since every table/list page now wraps its content in a `Card` and the boundary needs to actually read against the very-close-in-lightness `--background`/`--card` pair the design template specifies (`#faf8ff` vs `#ffffff`).
- Sidebar now has three responsive tiers matching `DESIGN.md`: full 260px-ish sidebar with labels at `xl` (1280px+), an icon-only collapsed rail at `md`–`xl` (768–1279px, tablet), and `MobileNav`'s dropdown below `md`. Collapsed nav links keep `aria-label`/`title` on the `<Link>` itself since the text `<span>` is `hidden` (not `sr-only`) at that tier.
- `DashboardTaskRow`'s header row (title/badges + action buttons + progress bar) didn't wrap at all below `sm` — at 375px it squeezed three fixed-width regions into one row, causing titles and due-dates to wrap word-by-word into an unreadable column. Fixed by stacking it (`flex-col` → `sm:flex-row`) instead of relying on the row never needing to reflow. If you add more inline controls to a row-based component like this, check it at 375px, not just desktop.
- Accessibility audit (spec §8): added `aria-label` to several `Input`s that only had a `placeholder` (search boxes in Companies/Tasks/Teams/Coverage, a couple of inline dimension-value editors) — placeholder text isn't a reliable accessible name. Checkboxes were already fine (wrapped in `<label htmlFor>`). Verified WCAG AA contrast (≥4.5:1) on every text/background pair in the new palette and the 7 recolored calendar statuses via a small relative-luminance script — worst case was 5.95:1. The one deliberate exception: card/table border contrast against the background sits around 1.6–2:1, well under the 3:1 non-text-UI-component guideline — this matches `DESIGN.md`'s explicit "ghost borders / subtle 1px border" intent (and the mockups' own look), not an oversight.
- Verification for task 23 was done with actual rendering, not just code review: `@playwright/test` is a devDependency but wasn't wired into any script — used a throwaway (uncommitted) script to sign in via the demo buttons and screenshot all 8 main pages at 1440/768/375px widths, reviewed visually. That's how the sidebar-collapse and dashboard-row bugs above were actually found; a Tailwind-class code review alone would have missed both.
- Task 24 — RLS tests (`tests/rls/`, run via `pnpm test:rls`, separate `vitest.rls.config.mts`, excluded from `pnpm test`/CI since they need the local Supabase stack up): the big gotcha is that a PostgREST UPDATE/DELETE denied by a policy's `USING` clause (as opposed to a `WITH CHECK` failure or a trigger-raised exception) is **not an error** — Postgres just filters the row out before the write, so the client sees `error: null` and 0 rows affected. `expect(error).not.toBeNull()` silently passes for the wrong reason in that case; you have to chain `.select()` on the write and assert `data` is an empty array instead. Cost 5 failing-for-the-wrong-reason tests before I caught it — grep this file for "USING clause" if writing more RLS tests. Fixtures (`tests/rls/fixtures.ts`) are upserted by a fixed natural key and never torn down by deletion, on purpose: `task_events`/`reassignment_requests` are append-only with no DELETE grant even for `service_role`, and hold plain (non-cascading) FKs into `tasks`/`task_instances`, so once any test triggers an audit-log insert, deleting the fixture task becomes impossible (permission error or FK violation). Re-running the suite just reuses the same rows.
- Task 24 — E2E (`tests/e2e/`, run via `pnpm test:e2e`, `playwright.config.ts`, single worker on purpose since specs share the real demo dataset): `globalSetup` calls the same `seedDemoData()` the nightly reset uses, then resets `nora@taskdeck.local`'s password to a fixed test-only value so a spec can sign into her real seeded account (via the existing manual `LoginForm`, not a new account) to play the "new assignee" role — `pnpm seed` afterward re-syncs only the two *demo-fixed* accounts' passwords, so Nora's stays at the E2E value until the next `pnpm seed` (harmless locally). Two things that will bite you if you add more specs: (1) the middleware redirects a signed-in user away from `/login` (`src/proxy.ts`), so switching accounts mid-test requires `page.context().clearCookies()` before re-visiting `/login`, not just navigating there; (2) an instance-level override's "Covering for X" label names the *original assignee* — for a team-assigned task that's the team name (e.g. "Covering for A/R"), not a person, so a test asserting a specific person's name needs to pick a person-assigned task row specifically (filter out rows with the "Group – …" chip).
